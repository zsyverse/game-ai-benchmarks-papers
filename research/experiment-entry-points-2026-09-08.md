# 从调研到实验：工件、依赖与比较协议

核查日期：**2026-09-08**。这是一份基于四项已收录工作的定向发布说明核查与实验设计建议，不是全库工件审计，也不是已完成的复现实验。检查了官方 README、指定依赖文件和 ByteSized32 的导入/超时实现；没有安装这些项目、下载大模型权重、调用付费生成 API 或运行第三方生成程序。

## 结论先行

- **先建立固定机制下的内容生成基线：** PCG Benchmark 提供问题接口，论文实验在另一个仓库；框架和实验版本都要固定。
- **研究可控分布与尺寸迁移：** Start Small 提供训练、条件模型、生成及分析流程，但“没有人工训练关卡”不等于“没有求解器”。
- **研究完整文本游戏代码：** ByteSized32 的参考/任务配对、反思和人工可通关定义值得复用；历史 API 和判分模型使原始分数不宜直接作为当前模型的对照。
- **研究动作驱动视觉世界：** Matrix-Game 第一版可作为具体的推理入口，但官方声明单次 65 帧推理需要至少 80 GB 显存；不能把这个版本与系列后续实时版本的成本或能力互换。

这些是针对不同目标的起点，不是四项方法的优劣排序。下面的环境信息只表示作者公开了什么，不保证在读者机器上一次安装成功。

## 1. 固定机制的生成与评测：PCG Benchmark

一手来源：[框架 README 固定版本](https://github.com/amidos2006/pcg_benchmark/blob/cd0f55b26c412a26e8797193e5417f5e651cf6cd/README.md)、[论文实验 README 固定版本](https://github.com/amidos2006/benchmark_experiments/blob/2c7ce70274c1a6c44386e9d3dc8e0d4b8dd27486/README.md)、[论文](https://arxiv.org/abs/2503.21474)。

- 框架 README 的 Installation 声明基本依赖为 NumPy 与 PIL；`make`、`content_space`、`control_space`、`info`、`evaluate`、`render` 和 `seed` 构成实验接口。不应据此推断所有问题的求解时间相同。
- `evaluate` 返回质量、多样性以及逐样本细节；提供 `controls` 时还评测可控性；多样性依赖样本之间的比较，不能当成与样本集合无关的单样本标签。
- 实验仓库的 Supported Generators 明确有 Random Search、μ+λ ES、GA；`run.py` 保存迭代状态，提供 `--steps` 和 `--earlystop`。相同迭代次数不自动等于相同候选评估次数，因为种群大小和每步操作可能不同。
- 实验 README 明确指出级联 `quality_control_diversity` 适应度会随种群改变。跨运行比较必须固定批大小、控制目标和多样性协议，不能把搜索过程中的单个最优 fitness 直接当最终生成分布质量。
- 当前框架 README 仍写“12 problems”，其表却列出 14 行（包括 tile 表示变体）。这不是 14 个新论文任务的证据。实验应记录实际环境 ID、表示和版本，不能只抄 README 的总数。

**建议的最小研究问题：** 在同一 `sokoban-v0` 或 `zelda-v0`、相同候选评估预算和固定控制集合下，比较三种公开搜索基线的质量—控制—多样性折中。该建议不表示本仓库已经运行比较。

## 2. 没有人工关卡，但仍需要判定器：Start Small

一手来源：[README 固定版本](https://github.com/yahiaetman/ms-level-gen/blob/2eb06c63850b226545fc942512ef23138ad05849/README.md)、[environment.yml 固定版本](https://github.com/yahiaetman/ms-level-gen/blob/2eb06c63850b226545fc942512ef23138ad05849/environment.yml)、[论文](https://arxiv.org/abs/2209.15052)。

- About 陈述两项假设：小尺寸随机探索能够以足够概率找到可玩关卡；小尺寸学习能帮助较大尺寸生成。不能把已测试游戏的结果外推为所有游戏都满足这些假设。
- Adding a new Game 要求 `analyze` 输出至少包含 `level` 和 `solvable`。Installation 明确 Sokoban 实验依赖作者的 `sokosolve` 求解器。
- README 指向 Python 3.9、PyTorch 1.11；但实际环境文件使用 `python>=3.9`、`pytorch>=1.11` 等下界，并从未固定 revision 的 Git 仓库安装 `sokosolve`。因此“有环境文件”不等于“精确依赖锁定”。
- Usage 要求训练后另建条件模型；论文使用拟合最终数据集 checkpoint 的 Bayesian GMM。只拿到生成器权重而忽略条件模型，不能按文中流程进行条件采样。
- 预训练下载说明只承诺保留运行生成器所需文件，不等于完整训练状态和日志。展示的关卡图来自生成结果中的**可玩子集**，不能以展示图推断总体可解率。
- README 将全论文脚本描述为 30 个实验、可能需要数日。这里不把该文字换算成本机耗时、GPU 小时或具体费用。

**建议的最小研究问题：** 将“目标尺寸见过/未见过”和“控制条件常见/稀有”分开，保存所有输出及求解预算；把失败样本留在总分母，同时报告成功样本中的多样性。小尺寸起步是否有效，需要通过这些分组观察，而不是只展示几张成功关卡。

## 3. 程序生成、执行与判分必须分开：ByteSized32

一手来源：[README 固定版本](https://github.com/cognitiveailab/BYTESIZED32/blob/48bb1467d7fc753a861ca0b0df07676d5413ed5e/README.md)、[validity.py 固定版本](https://github.com/cognitiveailab/BYTESIZED32/blob/48bb1467d7fc753a861ca0b0df07676d5413ed5e/bytes32/validity.py)、[EMNLP 论文](https://aclanthology.org/2023.emnlp-main.830/)。论文的样本数和判分限制见[前次全文记录](further-end-to-end-discovery-2026-09-05.md)。

- README 分开列出任务配对、代码生成、反思和自动评测；复用作者配对 CSV 与重新随机生成配对是不同实验条件。
- 作者提示：如果自定义实验文件，需同步修改手工标签 `data/test_eval.csv`。只换任务、不换评测标签会造成规格遵循分数无效。
- 官方流程依赖 OpenAI 或 Azure OpenAI API。重测时应记录确切模型 ID、日期和生成/评审模型，不能默认为当前服务与论文 GPT-4-32k 行为相同。
- 检查的 `validity.py` 通过 `importlib.import_module` 导入生成游戏（第 80 行），并通过 Unix `SIGALRM` 实现超时（第 19–21 行）。超时处理不是代码隔离措施。
- **本仓库的执行建议：** 将生成代码当作不可信输入，在不包含账户凭据、无默认网络和受限文件权限的隔离运行环境中评测。生成进程需要 API 密钥，不代表游戏执行进程也应该拿到密钥。此处是基于导入行为的安全建议，不是声称已完成全面安全审计。

**建议的最小研究问题：** 固定参考/任务配对、总生成预算和最多反思轮数，分别报告运行通过、规格遵循、物理一致性和人工可通关。自动玩家失败保留为“未找到解”，不要自动标为数学意义上的不可解。

## 4. 推理发布不是完整训练复现：Matrix-Game 第一版

一手来源：[Matrix-Game-1 README 固定版本](https://github.com/SkyworkAI/Matrix-Game/blob/71c3cd7f741311f8100f6cf9cde942b6c1378d11/Matrix-Game-1/README.md)、[对应论文](https://arxiv.org/abs/2506.18701)。这里仅讨论第一版，不把 Matrix-Game 2 或 3 的结果搬入。

- Overview 标注 17B 参数；Quick Start 说明推理依赖 Apex 与 FlashAttention-3。
- Hardware Requirements 列出 NVIDIA A100/H100，并声明一次 65 帧视频推理需要 **≥80 GB GPU memory**。这是该发布的作者要求，不是所有优化实现不可降低的理论下限，也不是本仓库的实测。
- GameWorld Score 的按键/鼠标准确性、物体和场景一致性属于不同指标；不能把人类成对偏好比例称为游戏胜率。
- 公开推理说明和模型链接可支撑选择推理实验入口，但不由此推断完整匹配训练数据、训练过程或全部评测配置已公开。原索引的 **Partial** 判断不因此升级。

**建议的最小研究问题：** 固定场景、动作序列、分辨率和硬件，分开测动作响应、返回旧地点的状态保持和长时漂移；再检查在线输入能否实际影响后续生成。离线处理完整动作脚本的片段不能直接提供实时交互延迟结论。

## 5. 跨论文比较的最小记录单

以下是本调研提出的实验报告建议，不是上述论文共同采用的统一标准。

| 必须记录 | 为什么会改变结论 |
| --- | --- |
| 论文身份、代码 commit、模型/权重版本、环境 ID | 同品牌不同代、更新的 benchmark 或表示变体可能不可直接比较 |
| 训练、验证、测试分割；关卡/场景/模板去重办法 | 未见种子不等于未见任务、未见地图或未见游戏机制 |
| 原始候选数、筛除数、成功数，以及失败原因 | 只评筛选后产物会把生成成功率变成条件成功率 |
| 搜索调用、反思轮数、solver/agent 预算、超时规则 | 更强评估器或更长搜索可改变可解判定和生成质量 |
| 全批多样性与合格子集多样性、控制目标集合 | 无效随机输出也可能高度不同；只看成功子集又会隐藏低产出率 |
| 同条件多个独立运行、区间估计、样本分组 | 同任务多个输出或同玩家多次试玩通常不是独立任务/玩家样本 |
| 硬件、分辨率、批大小、生成耗时、评测耗时、API 调用 | 生成快不等于含验证的总流程快，吞吐高不等于首帧响应快 |
| 人工选择、编辑、策展及评审模型 | 人工完成环节和模型偏好可能被误写为生成器能力 |

对同一批 N 个原始候选，可以补充报告：全体已证实可运行比例、全体已证实可通关比例，以及可运行子集内已证实可通关的比例。三者必须各自写明分母；这些观测成功比例不表示其余候选已被证明失败。无效或未完成判定的候选保留单独状态；只有证明不可解时才用“不可解”。不得把 ByteSized32 等论文的边际比例直接相除后称为论文报告的条件比例。
